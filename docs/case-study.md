# 实践记录：参考图到可运行 Live2D 的迭代

本 kit 来自一次持续迭代的实际项目：用户提供角色参考与设定图，要求制作可在 VTube Studio 中使用的模型，随后逐轮检查脸部、闭眼、接缝、嘴型和头发，最后增加网页输入模拟与动漫超分。

实践使用配置为 **GPT-6 Astra Ultra**，并结合本地脚本、图像生成、源码修改、专用超分及官方 Cubism Core 检查完成。这里记录的是一次成功实施中的方法和限制，不表示所有 agent 必须使用该模型，也不保证任意单图一键得到可交付的 Live2D。

本文是经过整理的工程经验，不是原对话导出。仓库不包含原角色素材、私人路径、运行模型、超分权重或官方 SDK。通用示例也不复刻该角色。第三方工具与许可见仓库的设置和第三方说明。

## 目标在迭代中变得具体

最初目标是“参考图变成 Live2D”。真正的验收需求随后逐项明确：

- 可爱、二次元的画风，五官端正，头发有清晰发束。
- 用户批准立绘后，保留这张脸，不再生成另一张近似脸。
- 导出真实 MOC3、运行资源和可编辑来源，不用静态视频冒充模型。
- 网页能加载实际模型、查看近景、调节参数，并显示原画作对照。
- 先模拟 VTS 风格的面部与半身输入；摄像头追踪留待后续。
- 用专用动漫超分保留原画结构；超分后重新检查运动和接缝。
- 最终 VTS 验收由用户执行，agent 不应替他们宣称验收结果。

可迁移的经验是先写清“批准哪些绘画”和“当前实际支持哪些运动”。没有独立眉毛、手臂、手指绑定的模型，不能靠加网页滑块就变成完整半身或手部捕捉。

## 迭代经过与转折

| 阶段 | 观察到的问题 | 采用的方法 | 留给后续 agent 的经验 |
| --- | --- | --- | --- |
| 工具可行性 | 架构文档不足以证明能导出可用 MOC3 | 阅读 psd2live 固定版本源码，走实际 CLI/内存图层入口，生成 PSD、CMO3 和运行资源，并用独立 Core 检查 | 先证明最小导出链，再投入角色美术 |
| 前期重绘 | 用户认为脸怪、眼睛斜、表情不可爱、头发成块 | 回到最早参考，重新确定正面立绘；经用户批准后固定脸部基准 | “工具能运行”与“用户喜欢画风”是两道不同验收 |
| 批准稿拆层 | 分别生成头部和五官后，模型仍和批准图差异明显 | 从批准母图直接切回脸、五官和头部原像素；校准裁切、眼角及中立参数 | 批准之后只补缺失内容，不为拆层再换脸 |
| 眼角与闭眼 | 眼角碎片、白角、半闭睫毛断开或发灰 | 测量原眼角，补闭眼皮肤，连续眼睑线过渡，眼白/虹膜收拢与分阶段透明度 | 必须检查关键值之间的过渡，不能只看 0 和 1 |
| 跨渲染器黑边 | VTS 中有矩形暗边，Web 中不明显 | 审查 atlas UV 和透明黑 gutter，增加正确图块的边缘延展，独立检查素材接缝 | 采样问题与素材几何问题要拆开诊断 |
| 网页输入模拟 | 需要预演面捕与半身联动，尚不接摄像头 | 使用合成跟踪输入映射到真实模型参数，显示源输入与输出，加入播放、暂停、时间线和复位 | 明确“模拟输入”“真实参数”和“设备追踪”的区别 |
| 嘴型联合输入 | `MouthSmile` 与 `MouthOpen` 同时调节出现肤色矩形 | 将皮肤留在脸底板，闭嘴层只提取唇线；做 SourceOver 重构及联合姿态检查 | 单参数通过不能证明组合参数通过 |
| 发根与颈部 | 大角度时旧描线、小洞、领口残留 | 分清随头/随身接片；保持重叠，局部修 RGB 而保留必要 alpha | 继续裁小可能消线却露洞，要修正确的材质和覆盖 |
| 动漫超分 | 素材像素明显；用户有本地模型 | 对比两种动漫模型，选择 AnimeVideo；神经网络处理 RGB，独立放大 alpha；保留原绑定和 UV | 超分不是重画，高清源与高清运行图集要分开管理 |
| 超分后胸前问题 | 发梢、背带和衣服有碎片错位 | 重新按真实轮廓描左右鬓发，去除可见服饰残片，排除肩部接片的衬衫；重建并重超分 atlas | 高清会放大旧拆层错误，结构修复必须先于最终超分 |

前期有多次技术检查通过但用户继续指出外观问题的情况。后来将原画对照、实际参数截图、局部 alpha 和组合动作纳入交付标准，才避免只围绕“能导出”优化。

## 实际使用过哪些工具

以下区别“实际执行”“辅助验证”和“只做可行性审查”。具体安装、固定版本与当前接口以 [setup.md](setup.md) 和 [MCP 说明](../mcp/README.md) 为准。

| 工具或方法 | 在本次实践中的作用 | 使用边界 |
| --- | --- | --- |
| Codex / GPT-6 Astra Ultra | 图像理解、计划、代码修改、并行审查和报告 | 用户对绘画的审美确认不可由测试替代 |
| 内置图像生成 | 正面立绘与缺失区域素材；曾用于重绘迭代 | 已批准脸最终使用原母图像素，后期超分没有再生成新脸 |
| psd2live，固定提交 `5526f2e16b57e5f83d34f33730d6fa26d8bc8695` | 真实图层装配、网格/参数/物理、PSD、CMO3 和 MOC3 导出 | 使用了本地适配与累计补丁；不能假定未修改的上游表现相同 |
| Kotlin manifest 导入器及 Java/Gradle | 把切片、遮罩、源坐标、层序转成可复现工程，扩展小特征网格与纹理处理 | 实際图层规划和源区域测量仍依赖角色本身 |
| 官方 Cubism Core Java / 本机动态库 | 独立解析 MOC、更新实际参数、读取顶点/透明度 | 不随本 kit 分发；数值有效不代表美术或 VTS 已通过 |
| WebGL 预览、浏览器自动化和 Playwright | 实际模型渲染、定点姿态截图、参数映射/交互/下载检查 | 不请求摄像头，不将合成输入称为真实面捕 |
| Upscayl 的 NCNN 命令行 | 在本地 GPU 上做专用动漫 4× 超分 | 只提高纹理采样，不修复分层语义、运动或遮挡 |
| `realesr-animevideov3-x4` | 最终选用的 RGB 超分模型 | 对当前画风更合适，其他角色应先局部对比 |
| `4x-AnimeSharp-fp32` | 对照候选 | 该画上增加了线条和虹膜对比，没有用于最终 atlas |
| `AtlasAlpha.java` | RGB 透明边延展、独立 alpha 缩放与重组 | 保持逻辑坐标，不凭网络输出重建 alpha 轮廓 |
| Python / Pillow / NumPy 等诊断 | 只读像素、alpha、哈希与重构误差，生成诊断报告 | 不把诊断脚本的成功当作完整视觉验收 |
| CLI-Anything Live2D | 已实际运行资源引用、严格校验和运行配置规则检查 | 当时实现不加载 Core，不检查眼角网格；没有用其占位模板冒充可运行模型 |
| CubismExternalEditMCP | 阅读源码并检查本地编辑器/接口可用性 | 没有成功连接编辑；当时接口也不支持任意 ArtMesh 顶点形状写入，未用于最终修复 |
| 多 agent 并行工作 | 一路检查源图轮廓，一路审查几何/工具边界，主 agent 集成 | 每次限定文件归属，避免同时改相同 manifest、引擎和导出目录 |

图像生成的额度等待曾影响素材补齐。因此实践将导出链验证、只读审查和素材生成解耦：等待绘图能力时先做独立工作，不凭订阅名称猜测图像额度，也不为赶进度把未生成素材说成已完成。

## 最后一次修复为什么有代表性

超分后的胸前发丝看起来像断开，最开始容易怀疑是超分移动了发丝或物理过强。追溯后，身体底图的背带本身是完整的；鬓发切片边缘和发间孔隙却保留了少量**可见**的服装像素。它们跟随头部及发丝，而身体上的背带跟随躯干，形成不同运动路径。

诊断过程中也修正了过度推断。裸 RGBA 图会显示 alpha=0 处保存的服装 RGB，不能据此说整块蓝饰和白背带都还可见。部分早期网格探测坐标恰好位于透明区域，其位移只证明两层路径不同，不能证明该处有可见错位。最终用实际导入 alpha、原画轮廓及 Core 截图共同确定要删除的内容。

修复没有把背带跟随头部，也没有固定发尾。左右发束分别描出主轮廓、细发丝和内部孔洞，保留原 RGB，只改技术 alpha；肩部接片另排除夹带的衬衫。其余脸、眼、嘴和身体绘画保持不变。

第一轮稀疏点检查得到 33/34 通过，但仍留下失败报告并复查那一个点；后续也没有为了所有边缘数值归零而侵蚀合法抗锯齿。最终一处非常低的边缘 alpha 被确认为连续发尖的抗锯齿，实际渲染没有形成独立服装碎片。这比单纯追求漂亮测试数字更接近真正的修复。

## 高清保持绑定的实际做法

素材和遮罩先在低分辨率验证。运行 atlas 由 2048×2048 放大到 8192×8192；先将邻近颜色延展到透明 RGB，使用 NCNN 对 RGB 做 4× 超分，原 alpha 独立用双三次插值放大，再合成 RGBA。

高清替换发生在原图集、网格和归一化 UV 建好之后。导出器保存逻辑页尺寸并校验原 atlas 的 SHA-256。若后续修改遮罩导致原 atlas 不同，旧高清图会被拒绝，必须重新生成。最终低分与高清 MOC 相同，说明这次提高清晰度没有重新绑定或改动形态。

9 张独立高清绘画源素材另行保存。最后一轮没有改变这些源绘画，所以复用已核对的高清源文件，只重做修改遮罩后的 atlas，并记录复用来源。最终运行图集与 CMO 使用高清纹理，源 PSD 和注册部件仍保留原绑定尺寸；交付时明确区分，未称其为高清分层 PSD。

下表是原项目的历史验证范围摘要，不是运行本仓库示例已经生成的报告。角色、参数与输出不同，需要重新建立自己的取样集；不能将这些数量当作验收门槛或直接继承通过结果。

| --- | --- | --- |
| 原画脸/眼选区最大通道差 1/255 | 一次原像素还原后的静止选区保真 | 所有表情、侧脸或新增补图与母图完全相同 |
| 嘴线复合最大误差 2/255、四边无非零 alpha | 原尺寸唇线/皮肤分离的重构质量 | 高清和动态绝不会出现接缝 |

| 最终 15 张胸前 Web Core 姿态 | 已知背带碎片与发梢断口在这些姿态中未复发 | 连续动作全覆盖或 VTS 通过 |
| 14 组网页输入及交付相关检查 | 模拟输入、播放/暂停、复位、视口和资源身份等功能 | 摄像头、麦克风或外部设备跟踪 |

用户曾明确确认此前版本在 VTube Studio 中验收成功。后来模型继续修改，最新第 10 版仅完成本地官方 Core、Web 和交付文件检查；**不能把此前版本的 VTS 成功写成第 10 版已在 VTS 验收**。可编辑 CMO 通过导出器回读，也没有被表述为已在官方编辑器人工验收。

## 适合复用的工作方式

1. 冻结批准画稿、量化中立对齐，再做动作；新增隐藏绘画与原像素分开记录。
2. 源图、遮罩、绑定、采样分别诊断；不要用重画解决错位，也不要用物理掩盖混入的衣服。
3. 每个可见材质只由正确运动层持有；交界靠正确补全和覆盖，不靠同一图案的两份错动副本。
4. 先修低分结构再超分。用哈希把高清纹理与它所属的低分布局绑定。
5. 独立审查很有帮助，但报告须能自我修正，尤其是透明 RGB 和网格位移的证据边界。
6. 验证应同时有数值检查、局部图像和组合动作；每份结论都绑定具体输出身份。
7. 功能声明跟随实际绑定与实际验收。合成面捕输入、Web 渲染、官方 Core 和 VTS 各写各的范围。
