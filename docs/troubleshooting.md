# 排查与修复：从可见缺陷追到素材、绑定和采样

本页记录本项目实践中有效的诊断方法。先看 [工作流程](workflow.md)，再按症状选择检查；不要把案例的坐标、参数阈值或测试数量照抄到新角色。案例经过和验收范围见 [case-study.md](case-study.md)。

## 先固定可复现的状态

修复前保留一份源素材、manifest、MOC、贴图和参数值。每张截图记录模型与贴图的 SHA-256、背景、视角、缩放、实际参数值。先暂停自动待机、物理驱动以外的时间输入、指针跟随、表情和捕捉模拟，避免滑块刚设好又被其他控制器覆盖。需要物理时另行记录输入序列和时间。

同时保存中立脸和缺陷姿态。只看孤立 PNG、模型能加载或画布哈希发生变化，都不足以说明模型画得正确。

按以下顺序定位，通常比立即重画或改物理更快：

1. **原画中是否已有问题？** 核对批准母图，而不是较旧候选图。
2. **拆层后是否出现？** 对照源坐标、裁切偏移、alpha、拼合结果。
3. **静止正常、运动异常？** 查层归属、父变形器、关键形态与遮挡覆盖。
4. **仅某个渲染器出现？** 查纹理采样、透明约定、裁切蒙版和实际加载版本。
5. **超分后才明显？** 先比较几何身份，再检查新增纹理、alpha 和原有缺陷。

## 症状索引

| 症状 | 优先检查 | 不应直接下的结论 |
| --- | --- | --- |
| 脸变宽、眼睛倾斜、不像批准原画 | 母图身份、裁切坐标、非等比缩放、初始参数、五官是否被重新生成 | 能眨眼就说明还原成功 |
| 嘴部出现矩形肤色块 | 闭嘴层是否包含不透明皮肤、脸部补底是否匹配邻域、两参数联合变形 | 加羽化一定能消除色差 |
| 仅 VTS 出现矩形黑边 | 资源身份、atlas gutter、边缘延展、运行端 alpha/过滤设置 | Web 无黑边就证明 VTS 没问题 |
| 闭眼有白角、彩色三角或断睫毛 | 眼白/虹膜残留、完整闭眼皮肤、睫毛遮挡缺口、开合过程透明度 | 完全闭眼一帧正常就算通过 |
| 头发间白色填充或大块黑衣跟着头发动 | 真正可见的 alpha、发丝轮廓、发间孔洞、服饰归属 | 直接删除所有白色或黑色像素 |
| 发根、颈圈、肩部出现断口或灰影 | 接片重复内容、头身不同运动路径、隐藏区域补全、层序 | 把发根继续裁短就能消除描线 |
| 高清图仍糊或绑定突然错位 | 导入器是否缩回原尺寸、UV/网格是否重建、HD 图集来源 SHA | 文件像素变大就等于有效超分 |
| CLI 全通过但仍很难看 | 检查实际工具实现与报告范围；运行真实 Core 并目检 | 文件头有效等于绑定和美术有效 |

## 脸部还原：批准后保留原像素

批准一张立绘之后，不要为方便拆层再生成一张“差不多”的头部。即使整体风格相似，脸宽、眼角、瞳孔、刘海缺口和嘴的位置也会变化；数值对齐无法补回同一张脸。

- 将批准母图设为固定基准，记录尺寸和哈希。
- 同尺寸叠加比较中立模型与原图，分别检查脸轮廓、眼睛和口鼻，不用不同裁切的截图凭印象对比。
- 统一原画坐标系与图层裁切坐标；裁切起点变化必须同步注册位置。
- 首先使用保守的头身变形强度。大角度旋转需要遮挡后内容与合适的形态，不能只增加角度范围。
- 补画睁眼原图中不存在的闭眼皮肤、口腔或遮挡后头发时，明确它们是新增素材；保留中立睁眼的原有像素和位置。

案例曾把批准脸从原画直接切回，静止脸/眼选区的最大通道差降到 1/255。这个结果只描述当时、当区域的像素还原，不能外推为所有表情或转头效果与原图完全相同。

## 嘴部色块：让皮肤留在脸上，让唇线随嘴动

常见错误是把“嘴＋附近一块皮肤”作为闭嘴图层。单独调整 `MouthOpen` 时可能不明显；再改变 `MouthSmile` / `MouthForm`，皮肤块会一同拉伸或淡出，和底下脸色形成矩形接缝。

修复分两部分进行：

1. 在脸底图的嘴区域建立与边界原像素匹配的皮肤底板，避免给整个矩形填单一肤色。
2. 闭嘴图层只保存唇线的颜色与 alpha；张嘴图层保存口腔及必要的边缘，不携带随参数移动的大块皮肤。

从带皮肤背景的细线提取透明前景时，不能只按颜色阈值挖掉浅色。需要考虑实际底板与 SourceOver 合成：`C = αF + (1−α)B`。低 alpha 的颜色恢复容易放大误差，边界还可能含抗锯齿，需限制不稳定值并与原图做复合比较。

检查包括：

- 原尺寸下把脸底板和闭嘴线重新合成，确认邻域颜色连续。
- 检查唇线切片的矩形四边，避免不透明皮肤一直延伸到裁切边缘。
- 对两组参数做网格取样，包含闭口、中间开度、大开口和不同笑容；再加入头部、身体和单眼输入。
- 用实际 Core 渲染验证，既看 100% 画面，也看放大的嘴角。

案例的唇线复合最大误差为 2/255，四边非零 alpha 为 0；这项数值测试只针对原分辨率拆层。高清后、动态时的外观必须另查。不要为了得到“零边缘像素”侵蚀实际延伸到边界的合法唇线；优先扩大裁切。

## 黑接缝：把 atlas 采样问题与真实拼接分开

若图层矩形边缘是不透明肤色，矩形外马上变成透明黑，双线性过滤或缩小采样可能混入暗色。不同渲染器的透明处理方式可能使问题在某一端更明显。本案例确认过缺少 atlas 边缘延展，但没有读取 VTS 内部 shader 状态，因此没有把推测的 alpha 混合配置当作已证实原因。

检查 PNG 中的 RGBA、实际 UV 范围、矩形周边空隙和运行端加载的文件，再修复：

- 为每个图块预留足够 gutter，并延展所属图块的边界颜色；避免相邻图块延展互相覆盖。
- UV 仍指向原图块，延展区不应被当作新几何画进角色。
- 在导出测试中证明图块内部像素未改、延展只取自正确图块。
- 分别检查直通 alpha / 预乘 alpha 约定；不要在未确认运行链路时随意预乘 PNG。
- 在浅色、深色和棋盘格背景以及适当缩小比例下复查。

案例使用过 16 原图像素的 padding / 边缘延展，属于该图集的实测配置。其他纹理尺寸、mipmap、缩放和过滤足迹需要重新评估；有限 gutter 不能保证任意缩小比例都无串色。

注意两种不同操作：**打包阶段的图块边缘 RGBA 延展**改善图集采样；**超分前透明区域 RGB 延展**给神经网络提供合理颜色上下文而保持 alpha 形状。不要把后者变成不透明填色，也不要用任一种延展掩盖真实缺失的绘画内容。

## 闭眼：验证整个交接过程，不只开与关

原画上睫毛可能被刘海遮住，在位图里本来就是几段。将它机械压扁或移动到闭眼位置，会把原先隐藏的缺口露出来。单独新增一条闭眼弧，也可能与眼角、眼白或发丝接不上。

实用处理顺序：

1. 测量每侧实际眼角、睁眼上睫毛曲线和闭眼素材端点。左右分别核对，不假定绝对镜像。
2. 补足闭合时应露出的眼皮和脸部背景，去掉原睁眼内容，保持相邻刘海边缘连续。
3. 为半闭状态准备连续眼睑线，沿测量的开眼曲线过渡；完整睁眼时恢复原睫毛。
4. 眼白、虹膜和睫毛分别安排几何与透明度。闭眼后不能在眼角保留有色的小三角。
5. 检查两条睫毛的交接。两层各 0.5 alpha 的 SourceOver 遮盖只有 0.75，可能形成灰带；先让接替的主体笔画完整覆盖，再让另一层退去。
6. 临近睁开时单独调节替代睫毛的厚度，避免闭眼笔画横跨整条睁眼线显得太粗。

按实际关键点在前后加密取样，包含左 Wink、右 Wink、双眼、向下看和转头。相邻参数值可能只差很小却正跨越显隐切换。几何连续、透明度合理和好看的眼型是三件事，要分别检查。

若仅 Web 近景出现眼白裁切阶梯，检查 SDK 裁切蒙版分辨率及设备上限。案例中提高 Web 蒙版精度改善过裁切粗糙，但它不会修复错误的眼皮形状，不能替代切片或绑定修正。

## 头发、服装与补片：一个可见图案应有明确的运动归属

“这块像素应该跟谁走”比“它现在位于哪个矩形内”更重要。身体上的背带应在身体图层；头发可以在它前面自由摆动，但头发图层不应顺带携带同一背带的残片。

这个原则不禁止重叠。为转头补画遮挡区域、将发根拆成上下过渡片、让接片藏在前景后，都可以是有意设计；要避免的是不同运动路径中重复露出同一段可见服饰或旧轮廓。

| 内容 | 通常归属 | 应检查的交界 |
| --- | --- | --- |
| 衬衫、背带、扣件 | 身体或专属服装图层 | 被发丝遮住后的完整形状 |
| 前发与细发尖 | 相应发束 | 发间孔洞、灰色线稿、物理根部 |
| 颈后头发 | 依设计拆成头部与身体过渡区域 | 头身反向运动时的覆盖 |
| 接片 | 它实际补全的材质 | 是否带入第二份皮肤、衣服或旧轮廓 |

案例的身体底图已有完整背带；移动鬓发边缘却残留少量可见的蓝饰边、白背带和黑衬衫。它们分别随头部、发丝和身体走不同路径，于是出现碎片错位。正确修复是沿真实发束与细发丝重做 alpha、挖掉发间衣服，并保持身体上的背带完整。把背带绑定到头、固定发尾或把发丝振幅降为零，只会绕开部分症状。

处理原则：

- 在源图坐标中分别描左右轮廓；不要因为发型看似对称就强制镜像。
- 把主发束、细发丝和内部透明孔分开表达。白发与白衣同色，黑衣与深线稿也会相近，简单颜色阈值不可靠。
- 保留真实的灰色描边和斜边抗锯齿。不要为了让某个探测点 alpha 变成 0，削掉连续发尖。
- 给发根留合适重叠并明确父级。删除旧描线若会露出洞，应该补全下方正确内容，或只修改 RGB 并保留覆盖 alpha。
- 审查羽化接片中的非目标材质。跟头运动的头发接片若包含衬衫，即使半透明，也会形成肩部灰影。
- 在低分版先验证头发独立内外摆、头身反向、抬低头和呼吸，再生成高清图集。

### alpha 证据的两个陷阱

**不要根据裸 PNG 的隐藏 RGB 判定污染。** alpha=0 的像素仍可存着原始服装颜色。应先按 alpha 合成到背景，或同时检查 RGBA。案例初查曾把透明区域残留的整块服装 RGB 误认为可见残留，随后用导入 PNG 的 alpha 将结论收窄到实际不透明碎片。

**网格位移不是可见像素证据。** 可以对同一源坐标在头发、身体网格中做重心插值，测出两层运动路径不同；若该坐标在头发层透明，测量只能说明“若存在像素会错开”，不能宣称那里确实有可见背带断口。要将运动测量、可见 alpha 与截图对应起来。

## 超分：先修好结构，再提高采样密度

超分使错误边缘更清楚，不会自动理解“这段白色是头发，那段白色是背带”。它也不能恢复一张原图未提供的真实侧面设计。

案例先比较 `realesr-animevideov3-x4` 与 `4x-AnimeSharp-fp32`；最终选择前者，是因为这张画的柔和肤色和低对比线稿保留得更合适。这个选择不是对全部动漫原画的排名，数值回缩误差更低的候选也不一定更符合批准画风。

保持已验证绑定的做法是：

1. 完成原分辨率的拆层、几何、层序和动作检查，生成确定的 atlas。
2. 在透明区域延展邻近 RGB，为网络减少透明黑边上下文；不改变可见 alpha。
3. 使用专用动漫超分处理 RGB，独立缩放原 alpha，再合成高清 RGBA。
4. 按相同整数倍率放大图集，保留布局比例、原画逻辑坐标与归一化 UV；不要因为分辨率变大重新绑定。
5. 用原 atlas 的 SHA-256 约束高清替换。素材、mask 或布局变了，旧高清图集必须失效并重做。
6. 比较低分与高清 MOC、物理及动作文件，确认未意外改变；再用同一组姿态逐帧视觉复查高清版。

若导入器按 manifest 的逻辑宽高重采样，直接把 4× PNG 换进原入口，可能又被缩回原尺寸。运行图集、独立高清源素材、PSD 和可编辑工程的实际分辨率要分别核实。不能把“有高清源图”写成“已交付高清分层 PSD”。

案例的最终运行 atlas 是 2048² → 8192²，CMO 引用高清图集；注册部件与源 PSD 保留原绑定尺寸。8K 是案例输出，不是最低要求。应查询 WebGL `MAX_TEXTURE_SIZE` 并考虑设备内存，按目标设备选择页大小或重新规划图集。

## 工具通过报告的范围

| 检查 | 可以说明 | 不能说明 |
| --- | --- | --- |
| 引用/JSON/PNG/文件头检查 | 文件存在、格式约定及基本配置合理 | MOC 内部网格可用、眼角正确 |
| 导出器自读回 | 与该实现自身一致 | 独立 SDK 或 VTS 一定兼容 |
| 官方 Cubism Core 解析和参数更新 | 实际模型可实例化，已采样状态的网格和透明度有效 | 美术好看、所有动作无接缝 |
| Web 实际 Core 渲染 | 已记录输入下的可见结果、网页交互 | 摄像头跟踪、VTS 的真实渲染 |
| 用户目标应用验收 | 指定版本在实际应用的已测行为 | 后续修改版自动继承通过 |

在实践所审查的版本中，CLI-Anything Live2D 是辅助静态检查工具；其参数列表可能来自动作/表情 JSON，不能当成 MOC 参数全集。CubismExternalEditMCP 被研究过，但没有实际连接编辑模型；当时接口不提供任意 ArtMesh 顶点形状写入。具体版本与能力边界见 [MCP 说明](../mcp/README.md)，升级后应重新核对实现。

## 收尾时怎样避免“修了但用户看到旧包”

- 校验导出目录、预览网页实际 HTTP 资源、运行 ZIP 中的 MOC 和贴图一致。
- 每次新构建记录指纹；旧报告只有在被验证内容确实未变化时才可有限复用，并注明复用范围。
- 保留最终构建、最终截图与最终报告的明确入口，不把中间失败候选写成已通过。
- 交付运行模型、可编辑来源、高清源素材和网页预览时，分别说明内容与重建方法。
- 用户要求自行验收 VTS 时，交付具体包和检查建议即可；Web 模拟不应访问摄像头或冒充真实跟踪。

这些检查应由症状和修改范围决定。案例的 34 个探测点、15 个胸前姿态或 196 个 Core 状态是当时的覆盖，不是其他角色照做后必然合格的固定指标。
